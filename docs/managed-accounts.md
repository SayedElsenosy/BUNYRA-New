# Managed accounts and separate sign-in portals
- Platform owner: /owner/login → /owner. Companies: /company/login → /company. The server verifies the matching identity type; a company account cannot obtain owner access by choosing another URL or platform mode.
- The platform owner creates a company and optionally its first company administrator in one database transaction. A duplicate username or seat-limit failure rolls the whole creation back.
- Company administrators create named internal accounts with a unique username, optional contact email, temporary password and company-scoped role. No email invitation, external signup or email verification is needed.
- Existing built-in roles, custom roles, and company/project overrides remain enforced server-side. Credential reset is restricted to a member of the selected company, excludes the caller and the platform owner, and revokes old sessions.
- Only the platform owner sets each company's active account limit (default 5; editable from company accounts). Active company administrators count toward it; disabled memberships do not. Creation and reactivation share a database trigger that locks the company row, including concurrent requests. Limits cannot be lowered below current active usage.
- Temporary passwords must be replaced at /account before any business API can be used. Self-service password changes verify the current password and rotate sessions. Account profile changes preserve user IDs and the platform owner singleton.
- Passwords use native scrypt (N=16384,r=8,p=5; per-account 128-bit salt). Only hashes are stored. Session tokens contain 256 random bits, are hashed in the database, expire after 12 hours, and are sent in a host-only HttpOnly, SameSite=Lax cookie with Secure in production. Password version checks reject stale login/reset races. Suspensions and membership disabling revoke sessions.
- Login throttling persists in the database (10 attempts per normalized username / 15 minutes, 60 per Cloudflare-verified source IP). Do not trust client-supplied X-Forwarded-For.
- Existing verified owner sessions remain usable only until the owner sets local credentials from Account Settings. The first owner portal login can verify the existing managed password once and preserve the same owner ID while enabling internal credentials. A shorter legacy password redirects to account setup. No external provider is required for subsequent account sign-ins. Existing company provider sessions cannot bypass internal account provisioning.
- Public auth signup and invitation acceptance endpoints are closed. Legacy invitation records remain available for audit compatibility; new company/request approval flows create no invitations.
- Apply db/013-managed-accounts.sql before deploying this version. Credentials/session tables have RLS and no grants to the tenant role. They are accessed only by the server after authorization.
- Verification: npm run typecheck; npm run test:accounts on the dedicated fixture database. The test script refuses a database without the named test owner. Existing identity and company lifecycle checks also cover compatibility.
- On a future custom domain, use the same relative URLs. Cookies are host-only, so users sign in again on the new domain. Internal accounts need no external OAuth callback setup.
